# Gennect CRM — система для УБТ-команди

Робочий MVP під цикл **ресурси → фарм → контент → залив → трекінг → виплати → аналітика**.
Закриває те, що зазвичай ламається в Google Sheets на 15+ людях: облік акаунтів і девайсів,
звʼязка «креатив → акаунт → публікація → конверсія», автоматичний розрахунок ЗП і розрізи ROI.

Node 22, фронтенд — ES-модулі без збірки. Двигун БД перемикається змінною:
без неї SQLite (нічого не треба ставити), з `CRM_DATABASE_URL` — PostgreSQL.
Єдина рантайм-залежність — драйвер `pg`.

## Запуск

```bash
git clone https://github.com/eugene263/CRM.git && cd CRM
cp .env.example .env                       # мінімум — задати CRM_SECRET_KEY
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # ключ шифрування

npm run seed          # створює власника + демо-дані (28 акаунтів, 400+ заливів, 30 днів статистики)
npm run seed -- --admin   # тільки власника, без демо — для бойового старту
npm start             # http://localhost:3000
npm test              # 16 інтеграційних перевірок: RBAC, постбеки, ЗП, аудит
```

Демо-логіни після сіду: `owner@gennect.local / gennect-admin`, далі `head@`, `lead.a@`,
`creator1@`, `editor@`, `farmer@`, `finance@gennect.local` — пароль `demo1234`.
Зайдіть під крієйтором і під власником: видно різні дані, це і є перевірка RBAC.

Docker: `docker compose up -d --build` (адмінка 3000, постбеки 3001, щоденний бекап бази у `./backups`).

Хостинг з одним портом (Railway, Render, Fly): достатньо змінних `CRM_SECRET_KEY`,
`CRM_ADMIN_EMAIL`, `CRM_ADMIN_PASSWORD`, `CRM_SECURE_COOKIE=1` і тому для бази на `/data`.
Порт застосунок бере з `PORT`, постбеки в такому режимі обслуговує основний процес
(окремий лістенер вимикається автоматично), база створюється при першому старті.

## Пошук клієнтів (prospecting)

Ручний пошук бізнесів із фіксацією того, **де знайшли** і **куди написали**.
Три рівні: список → лід → контакт → тач.

- **джерело обовʼязкове**: канал (Google Maps, Instagram-пошук, хештег, Ad Library…),
  запит, URL, хто і коли знайшов, сигнали («ллє рекламу», «мертвий акаунт»).
  Без цього поля конверсію по джерелах не порахувати — тому API не приймає лід без нього
- **тачі**: канал, напрямок, з якого нашого акаунта, шаблон, повний текст, статус доставки,
  автоматичний номер тача. Тач без тексту не зараховується
- **автоматика**: тач → статус «Написали»/«Фолоу-ап», задача на фолоу-ап, дата наступного контакту;
  вхідний тач → «Відповіли» + сповіщення; «не зараз» розморожується сам; лід без руху 14 днів
  повертається в чергу
- **захист від подвійного дотику**: якщо ліду писали за останні 3 дні, API віддає 409
  з іменем того, хто писав, і вимагає підтвердження
- **дедуплікація**: точний збіг по домену, телефону, email, Instagram-ніку, Google Place ID
  плюс нечітке зіставлення назви в межах міста; злиття переносить історію тачів, а не видаляє її
- **чорний список** (домен/email/телефон/нік/назва) блокує створення ліда взагалі
- **статуси й довідники редагуються в UI** — таблиці `lead_statuses` і `dictionaries`
- **екран «Мій день»**: відповіді, прострочені фолоу-апи, ліди без жодного дотику
- **воронка**: конверсія по джерелах, по каналах звʼязку і **по номеру тача** — видно,
  чи команда не здається після першого повідомлення

Масова вставка: стовпчик посилань або `@ніків` → ліди з розпізнаними Instagram/TikTok
профілями й спільним джерелом.

## Плани та норми менеджера

Норма не вписується зі стелі — вона рахується **зворотно від цілі по клієнтах**:

```
4 клієнти → 20 зустрічей → 67 відповідей → 834 опрацьованих ліди → 2084 тачі
за 21 робочий день на 1 людину: 57 лідів і 100 тачів на день
```

- калькулятор у розділі «Плани та норми»: крутите коефіцієнти — бачите норму;
  коли в базі набереться 200+ лідів, коефіцієнти підставляються **з вашої статистики**,
  а не з галузевих орієнтирів (`/api/kpi/coefficients` чесно каже, скільки ще бракує)
- одразу показує, **скільки акаунтів/скриньок** потрібно під таку кількість тачів:
  за лімітів 30–50 на акаунт 100 тачів = мінімум 3 акаунти
- розрахунок застосовується як плани: денні норми + місячні цілі на обраних людей
- **контроль якості вбудований у факт**: у план іде не «створено», а «валідно» —
  лід без сайту, соцмережі й контакту не рахується; дубль не створюється взагалі;
  дискваліфікований як «не наше гео / закрились / занадто малі» **знімається заднім числом**
  і потрапляє в показник браку; тач без тексту або з блоком/bounce не зараховується
- норма множиться на **рампап** новачка (тиждень 1 — 30%, далі 50/70/85/100%) і на
  **завантаженість дня** з робочого календаря: відпустка чи лікарняний не перетворюються
  на невиконаний план
- **ліміти акаунтів**: API зупиняє тач, коли скринька або нік вичерпали добовий ліміт
  (429 з підтвердженням), у «Мій день» видно залишок по кожному акаунту
- **бонус** — ступінчастий (70% → 0.5, 90% → 0.8, 100% → 1.0, 120%+ → 1.3) з гейтом
  за браком: перевищив 15% — бонус за кількість не виплачується. Рахується всередині
  наявного розрахунку ЗП
- сповіщення: ранковий план, пінг о 14:00 при виконанні нижче 30%, підсумок дня
- екран тімліда: факт/план по кожному, брак, час останнього тача, ліди без руху

## Сейф доступів

Окремий модуль під те, що зазвичай живе в нотатках і перепискax: пошти, картки,
гаманці, партнерські кабінети, 2FA-сіди.

- секрети (`password`, `recovery`, `2FA seed`, нотатки) шифруються AES-256-GCM і **ніколи** не їдуть у списку
- логіни в списку маскуються (`ma***@example.com`) для всіх, крім власника ресурсу й того, кому доступ виданий
- розкриття — поштучним запитом, кожне пишеться в аудит; є **добовий ліміт на роль**
  (крієйтор 5, тімлід/фармер 50, власник 200) і алерт у Telegram при сплеску розкриттів за годину
- код 2FA генерує сама CRM з збереженого сіда — сід із сейфа не виходить
- **видача під розписку**: кому, коли, до якої дати, стан при видачі й поверненні;
  після повернення пароль автоматично позначається «потребує ротації»
- **часові доступи**: `due_at` минув — доступ відкликається фоновою перевіркою
- **чутливі категорії** (картки, гаманці, кабінети) вимагають апруву тімліда або хеда
- **офбординг однією дією**: сесії вбиті, всі доступи відкликані й позначені на ротацію,
  девайси повернуті на склад, акаунт вимкнений (не видалений — історія лишається)

## Ролі

Матриця прав живе в БД (`roles`, `role_permissions`), а не в коді: розділ «Ролі та права»
дає редагувати рівень (`—/читання/запис/повний`), скоуп (`свої/команда/усі`) і перелік
прихованих полів для кожної пари роль×розділ, створювати власні ролі й міняти капабіліті
(розкриття секретів, експорт, розрахунок ЗП, адмін-права, добовий ліміт розкриттів).
Зміни діють одразу, без перезапуску. Права власника незмінні за визначенням.
Дефолти з коду накочуються в БД при першому старті, нові розділи автоматично
додаються всім ролям з рівнем «немає доступу».

| Роль | Що бачить |
|---|---|
| `owner` | усе, включно з налаштуваннями й аудитом |
| `head` | усе, крім редагування аудиту |
| `teamlead` | свою команду: ресурси, заливи, креативи, витрати, виплати команди |
| `creator` | свої акаунти, свої заливи, свої креативи, свою ЗП. **Не бачить** ставок оферів, партнерок, чужих даних і загального ROI |
| `editor` | креативи, версії, свої задачі |
| `farmer` | ресурси (акаунти/девайси/SIM/проксі/пошти), може відкривати секрети |
| `finance` | офери, партнерки, витрати, конверсії, ЗП, P&L, аудит |
| `analyst` | читання аналітики без секретів і правил ЗП |

Матриця прав — `src/rbac.js`, одна таблиця. Додати роль = додати рядок.

## Трекінг

Лінк: `https://<host>/r/<slug>` → редірект на офер із підстановкою
`sub1=account_id`, `sub2=creative_id`, `sub3=user_id`, `sub4=post_id`, `click_id=<id>`.

Постбек партнерці (токен видається при створенні партнерки, поле `postback_token`):

```
https://<host>:3001/pb/<token>?click_id={click_id}&status=approved&event=dep
   &payout=45&currency=USD&external_id={conversion_id}
```

- `status`: `hold|pending|lead` → холд, `approved|confirmed` → апрув, `rejected|trash` → відхилено, `paid` → виплачено
- `event`: `reg|dep|sale|click`
- дедуплікація за парою `partner_id + external_id`; повторний виклик **оновлює статус**, а не створює дубль
- якщо `click_id` знайдено, звʼязка акаунт/креатив/крієйтор підтягується автоматично; інакше беруться subid
- постбеки слухає окремий процес (`CRM_ROLE=postback node server.js`), щоб сплеск конверсій не клав адмінку

Якщо у вас уже є Keitaro/Binom — лишайте трекер собі, а сюди шліть постбеки тим самим форматом.

## Формула ЗП

`ЗП = фікс + % від профіту + бонус за KPI`

- профіт крієйтора/монтажера/фармера — його апрувнуті конверсії мінус витрати, повішані на нього
- профіт тімліда — по його команді; хеда/власника — по компанії
- бонус нараховується, коли факт за метрикою (`posts` / `deps` / `profit`) досяг цілі
- правило шукається спершу персональне, потім по ролі, з урахуванням `active_from`
- холд у профіт не входить — платимо з апруву
- періоди зі статусом «виплачено» перерахунок не чіпає

Налаштування — розділ «Правила ЗП», розрахунок — «Фінанси → Розрахунок ЗП» (перегляд, потім «Нарахувати»).

## Безпека

- паролі акаунтів/пошт/проксі шифруються AES-256-GCM, ключ лише в `CRM_SECRET_KEY`, у БД його немає
- у списках секрети завжди `••••••`; розкриття — окремий запит із роллю `secrets` і записом в аудит
- експорт CSV доступний не всім ролям, пишеться в аудит і містить водяний знак з email того, хто вивантажив
- паролі співробітників — scrypt; 2FA — TOTP; сесії в БД з терміном дії, кука `HttpOnly; SameSite=Lax`
- rate-limit на логін (10/хв з IP) і на постбеки (600/хв на токен)
- адмінку тримайте за VPN або IP-whitelist на nginx; назовні світіть лише порт постбеків
- бекап бази — щодня (у compose є окремий контейнер); раз на місяць перевіряйте відновлення

## Бекапи та міграції

- `src/backup.js` раз на добу робить `VACUUM INTO` — консистентний знімок навіть під
  навантаженням — у `backups/` поруч із базою, з ротацією (`CRM_BACKUP_KEEP`, типово 14).
  Це рятує від «видалив не те», але **не замінює зовнішню копію**: том хостингу — не бекап.
  Для проду забирайте файли з тому в S3/R2 або окремий сервер і раз на місяць перевіряйте відновлення.
- `src/migrate.js` — версіоновані міграції: нові колонки накочуються при старті,
  застосовані ID зберігаються в `settings`, ручні `ALTER` на проді не потрібні.

## Двигуни БД і перенесення даних

```bash
npm start                                   # SQLite: ./data/crm.db
CRM_DATABASE_URL=postgres://... npm start   # PostgreSQL
npm test        # прогін на SQLite
npm run test:pg # той самий набір на чистій базі Postgres
```

Запити в коді написані діалектом SQLite, для Postgres вони перекладаються в
`src/db-pg.js` (`?` → `$n`, `datetime('now')`, `date(col)`, `julianday`, `strftime`,
null-safe `IS ?`). Часові мітки в обох двигунах зберігаються текстом
`YYYY-MM-DD HH:MM:SS`, тому порівняння, `BETWEEN` і сортування поводяться однаково.
Схема лишається одна (`src/schema.sql`), типи під Postgres переписує `toPostgresDdl`.

Перенести наявну базу:

```bash
CRM_DB=./data/crm.db CRM_DATABASE_URL=postgres://... node scripts/migrate-sqlite-to-pg.js
```

Скрипт створює схему, переливає таблиці в порядку залежностей і підтягує
лічильники `identity` — після нього id не конфліктують з новими записами.

## Масштабування

1. `clicks` і `conversions` винесені в окремі таблиці навмисно — вони першими їдуть
   у ClickHouse, решта модулів їх торкається лише через `src/analytics.js`.
2. Фонові задачі зараз у `setInterval` в `server.js` — виносяться в чергу без змін
   у бізнес-логіці.
3. Приймання постбеків піднімається окремим процесом: `CRM_ROLE=postback node server.js`
   з тією ж `CRM_DATABASE_URL`. На PaaS це окремий сервіс — деплой адмінки не втрачає конверсії.

## Помилки

`CRM_SENTRY_DSN` вмикає відправку помилок у Sentry (без SDK, один POST на подію):
500-ті з API, падіння фонового воркера, `uncaughtException` і `unhandledRejection`.
Без змінної все пишеться лише в лог.

## Далі (за етапністю з ТЗ)

- **v1**: інтеграція з Keitaro/Binom по API, S3/R2 для файлів креативів із превʼю, звірка сум з API партнерок
- **v2**: ClickHouse, прогноз вигорання звʼязок на історії, мобільний інтерфейс для крієйторів, публічне API

Автозбір метрик із TikTok/IG свідомо не робили: він найнестабільніший і ламається щомісяця.
Поки що — ручне внесення або імпорт CSV, як і рекомендує етапність.

## Структура

```
.
  server.js            точка входу: адмінка/API + окремий сервіс постбеків
  src/
    schema.sql         схема БД
    db.js              доступ до БД, аудит
    entities.js        опис сутностей → з нього будуються і API, і форми в UI
    rbac.js            матриця прав, скоупи, приховування полів
    api.js             REST: генерик-CRUD + постбеки, редіректи, експорт, імпорт
    auth.js            сесії, 2FA, паролі
    crypto.js          scrypt, AES-256-GCM, TOTP
    analytics.js       дашборд, розрізи, вигорання, життя акаунтів
    finance.js         ЗП і P&L
    telegram.js        черга сповіщень
    seed.js            власник + демо-дані
  public/              інтерфейс (ES-модулі, без збірки)
  test/smoke.test.js   інтеграційні перевірки
```

Додати поле в будь-який розділ — один рядок у `src/entities.js`: воно зʼявиться і в API, і в таблиці, і у формі.
